# Security review: the public API (A6)

A review of the fork's public REST API (`src/features/public-api/`, `src/app/api/v1/<resource>`) and what it touches
(webhooks, uploads, the Shopmonkey archive), before it is put in front of a client's integration. Done 2026-11-24 on
`fork/A6-hardening`, by reading the code, running the tests named below, and `npm audit`.

Severity is for this system as deployed (self-hosted, one container behind a reverse proxy): **high** means an
outsider or another workshop can read or change data, or take the service down cheaply; **medium** needs a valid key,
a misconfiguration, or a rare race; **low** is defence in depth.

**Open high-severity findings: none.**

## Findings

| # | Area | Finding | Severity | Status |
| --- | --- | --- | --- | --- |
| 1 | Key storage | Only an HMAC-SHA256 of the whole key is stored, peppered with `API_KEY_PEPPER` (or a value derived from `BETTER_AUTH_SECRET` under its own label); the key is shown once. `keys.server.ts`. | — | Sound |
| 2 | Timing | The key check compares hashes with `timingSafeEqual` after a length check (`keys.server.ts`); webhook signatures are compared the same way (`webhooks/Lib/sign.ts`). | — | Sound |
| 3 | SSRF | Webhook URLs are checked when saved and again when delivered (`webhooks/Lib/ssrf.ts`, `webhookService.server.ts`, `deliver.ts`), and redirects are not followed (`redirect: 'manual'`). But the delivery's check resolves the name and the fetch resolves it again (`deliver.ts`), so a name that rebinds between the two (DNS rebinding) reaches a private address, and the first 4 KB of what it answers are kept in the delivery log. The fork makes webhooks reachable by any key with `settings` permission (`Writes/records.ts`). | Medium | **Accepted**: upstream's code, and the same for a webhook saved in the app. The fix is to pin the checked address (an undici `Agent` whose `connect.lookup` runs `isPrivateAddress`); raise it upstream. |
| 4 | Tenancy | Every query is scoped by the key's workshop, lookups by id included; another workshop's id answers exactly like one that doesn't exist (404). Ids in the path: one sweep over every route and method, which also shows every record it aimed at unchanged (`public-api-isolation.db.test.ts`). Ids in a request body (a vehicle's `customerId`, a line's `inventoryPartId`): the A4 write tests (`public-api-write-tenancy.db.test.ts`). | — | Sound |
| 5 | Logs | A failed request logged the whole error object, and so did a failed idempotent store; a service's message or a Prisma error's meta can quote what was sent. | Medium | **Fixed**: both log the method, path, the error's class and code, and the stack's frames without its message (`withPublicApi.ts`, `idempotency.ts`, `errorFrames.ts`, tested). No log in the API prints a key, a body or a header. |
| 6 | Errors | A 500 answers `server_error` and a fixed sentence; a 400 lists the request's own fields and messages (zod). A plain `Error` is answered as a refusal with its message, and Node's file system errors are plain Errors: a failed `mkdir` in an upload answered 400 with the server's path. | Low | **Fixed**: an error carrying `code`, `errno` or `syscall` is ours, a 500 (`writeRoute.ts` `isSystemError`, tested). |
| 7 | Body size | `/api/v1` is outside the proxy whose body limit (2 GB, `next.config.ts`) covers the rest of the app, so nothing limited a body there: an upload without a `Content-Length` was read whole before its size was checked, and a JSON body was read whole at any size. A key with any write permission could hold that much memory per request. | Medium | **Fixed**: uploads, and JSON bodies up to 1 MiB (the most the app's own server actions take), are read as they arrive and stopped past their limit with a 413, or refused before reading when their `Content-Length` says so (`writeRoute.ts`, `readBounded`, `readJsonBody`; tested with an endless stream and on a route). Upload types are checked by their first bytes; stored names are the server's. |
| 8 | IP allowlist | Compared as exact strings: `::ffff:203.0.113.7` didn't match `203.0.113.7`, nor `2001:DB8::1` match `2001:db8::1`. | Low | **Fixed**: both sides in one spelling (`Lib/ipAddress.ts`, tested). |
| 9 | Client address | The allowlist and the failed-authentication block (30 a minute, before any key lookup) read `X-Real-IP`, or `CF-Connecting-IP` when trusted, else the last `X-Forwarded-For` entry, as upstream's rate limiter does. Next fills that header from the socket only when the client didn't send one, so none of them is trustworthy unless a proxy overwrites them; the shipped `docker-compose.yml` publishes port 3000 directly, where a caller can send any address: to get past an allowlist, or to spend another address's failures and lock its keys out. The brief asked whether a valid key should get past a blocked address. | Medium | **Changed**: a key that has authenticated from an address in the last 10 minutes gets past that address's block, until it fails 30 times a minute itself, so a spoofer can't lock an integration's working key out without sending its prefix too (not a secret: Settings → API keys shows it, and the key's creation is in the audit log); a key idle for 10 minutes, or a new one, waits out a block. Addresses are counted in one spelling, at most 64 characters, and a key's own failures apart from its address's (`rateLimit.ts`, tested). No opt-in switch to trust or distrust `X-Real-IP`: the API reads the address with upstream's `clientAddress`, which its own rate limiter shares, and a switch only the API honoured would leave the app's limiter reading the header anyway; the fix is the proxy, as for upstream. API.md §2 and the API keys screen say a proxy must overwrite `X-Real-IP`; a deployment behind one (the documented production setup) is not affected. |
| 10 | Key lifetime | A key outlives the admin who made it: it belongs to the workshop, so an integration doesn't stop when a member leaves. | Low | **Accepted**: owners and admins see every key in Settings → API keys and revoke it there (at once); a key's scope is its role. |
| 11 | Rate limit | 120 requests a minute per key, in process. Several app instances would each allow 120. | Low | **Accepted** for the single-container deployment; note it before scaling out. |
| 12 | CORS | No CORS headers: browsers can't call the API from another origin with a key. | — | Sound (server-to-server only). |
| 13 | Idempotency | Stored answers are scoped by workshop and key; a different body under the same key is a 409. What it can't promise is in API-GUIDE.md (a retry after 5 minutes when storing the answer failed runs the write again). The purge test deleted every expired row in the shared test database. | Low | **Fixed** (the test ages only its own row and purges at the real time). The limits are documented. |
| 14 | Webhook payloads | A fork event's `data` is the API's serialized resource, read scoped by workshop only once a webhook subscribes (`eventHook.ts`); one that can't be read goes as its id. Signed as upstream's are. | — | Sound |
| 15 | Archive access | `/source-records` and `include=source` hand out the source's raw payload (which can hold more than a resource shows); both need `read:settings`. | — | Sound |
| 16 | Dependencies | `npm audit --omit=dev`: 3 high, 3 moderate, all upstream's: `effect` (ReDoS in a schema's template-literal regex) through `prisma` → `@prisma/config`, and `minimatch` 5 through `exceljs` → `archiver` 5 → `readdir-glob`. Neither is reachable with request data: Prisma's config parses the install's own `prisma.config.ts`, and that `archiver` is exceljs's own copy, used only to write the import template's xlsx (`import/Lib/template.ts`), with no glob from a request (the backup export's own archiver only calls `file` and `append`). | Low | **Accepted**, upstream's to bump; re-run `npm audit` after each upstream merge. |
| 17 | Keys on the Team page | A key's service user is a member (its role is the key's scope). The Team page offered to remove it, which made the key answer 401 "revoked" while Settings → API keys still listed it active, and to give it the technician app, which would sign a phone in as the key; the subscription page counted it as a member. | Low | **Fixed**: labelled as a key, no Remove and no app on the screen; removing it, marking it a technician, linking a technician to it (the work board, `/technicians` in the API) and issuing it an app code are refused by the actions and services too (an open tab from before, or an API call); given the Technician role, it takes the role (its scope) but no place on the board; the member pickers (work board, report schedules) don't offer it, and a restore never links a technician to it; not counted as a seat on the Team or subscription page (`team-api-key-member.test.tsx`, `api-key-member-refusals.test.ts`, `api-keys-team.db.test.ts`, `technician-service.test.ts`). |
